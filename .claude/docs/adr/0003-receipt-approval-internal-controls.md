# 0003. レシート承認ワークフローの内部統制強化

## Status

Proposed

## Date

2026-05-21

## Context

マルチ店舗・多段承認・小口現金帳機能の導入後、内部統制・会計の正確性の観点で複数の指摘が挙がった。経費精算システムとして致命的なものを含む：

- **承認後の改ざん**: レシートはどのステータスでも誰でも編集でき、`approved`/`paid` のレシートも金額・日付を後から書き換えられた。
- **差戻しの行き止まり**: `rejected` レシートを修正しても申請中に戻す導線がなく、差し戻された経費が宙に浮いた。
- **残高の不整合**: 小口現金帳が差戻しレシートも出金計上し、現金残高が実態と乖離した。
- **通知の不在**: 各承認段階で「誰かが見に行く」運用に依存し、滞留や差戻しに気づけなかった。
- **誤操作の不可逆性**: 誤承認を巻き戻せず、複数件の承認も1件ずつ詳細画面を開く必要があった。

これらに対し、認証・認可の基盤（Firebase Auth + Supabase anon key 直アクセス、ADR 0001）を大きく変えずに、どこまで統制を強化するかが論点となった。RLS（行レベルセキュリティ）の導入は認証基盤の改修（Firebase → Supabase JWT 連携）を伴う大規模作業である。

## Decision

**クライアント側のワークフロー制御とデータ層のガードで内部統制を強化し、RLS によるサーバー側強制は別タスクに切り出す**段階的アプローチを採用した。

本変更で実施：

- **編集ロック**: `isReceiptEditable()` を導入し、編集可能ステータスを `pending` / `rejected` のみに限定。詳細・編集の両ページで制御し、編集ページは直 URL アクセスもブロックする。
- **再申請フロー**: `rejected` レシートを申請者本人が `pending` に戻し、承認・差戻し情報をクリアして承認フローを最初からやり直せる導線を追加。
- **小口現金帳**: 差戻しレシートを残高計算から除外（`activeReceipts`）。入金記録の編集機能を追加し、入金の作成/更新/削除すべてを監査ログに記録する。
- **通知**: アプリ内通知テーブル `tks_notifications` とヘッダーの通知ベルを追加。申請・各段階の承認・差戻し・再申請・支払で関係者に通知。メール送信は Route Handler 経由（Resend）とし、`RESEND_API_KEY` 未設定時はアプリ内通知のみで動作する。
- **承認の取り消し / 一括承認**: 各承認者が自ステージを1段階巻き戻せるようにし、一覧画面で複数レシートをまとめて承認できるようにした。
- **楽観ロック**: `updateReceipt` に `expectedStatus` を追加。取得後に他者が状態変更したレシートの上書き（特に一括承認時）を防ぐ。

RLS は ADR を分けて扱う（`tks_receipts` のステータス遷移制約、`tks_notifications` の受信者スコープ、`tks_cash_deposits` の店舗スコープ）。

## Consequences

### Positive

- 承認後のレシート改ざんが UI 経路で防止され、差戻し経費が再申請で確実に処理される。
- 小口現金帳の残高が現金の実態と一致し、入金記録の変更も監査証跡に残る。
- 通知により承認の滞留・差戻しが関係者に届き、運用依存が減る。
- 誤承認の巻き戻し・一括承認で経理／承認者の手間が減る。
- 認証基盤を変更しないため、変更範囲とリスクが限定的でレビューしやすい。

### Negative

- 編集ロック・承認権限・楽観ロックはクライアント／データ層の制御であり、Supabase anon key を直接操作すれば回避できる。サーバー側の強制は RLS 導入（別タスク）まで未達。
- メール送信 Route Handler は宛先を登録ユーザーに限定するが、認証は未実装で、認証付き API への移行は RLS タスクに含める。
- 通知はクライアントからのポーリング方式で、リアルタイム性は限定的。

## Compliance

- 編集ロック・楽観ロックの回帰は型チェックと、`isReceiptEditable` / `expectedStatus` のユニット／E2E テストで検証する。
- RLS 未導入であることを既知の制約として残し、後続の RLS 用 ADR とタスクで追跡する。
- `tks_notifications` のマイグレーション適用を本番反映手順に含める。
